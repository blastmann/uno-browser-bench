# Browser Observation 意图识别技术实验报告

**实验日期：** 2026-09-19  
**实验平台：** 本机 Windows，GPU 推理/训练  
**实验对象：** NanoJev（Qwen3-0.6B 基座）与 Decider-2B  
**数据范围：** 脱敏合成 Browser Observation 数据 + 本机 Edge 历史生成的本地弱标签 trace

## 1. 先给结论

当前两个模型都不适合直接作为“浏览器打开后就自动决定下一步”的常驻决策器。

比较合适的用法是：

1. 先在本地做候选意图排序；
2. 只有模型很有把握时才推荐一个候选；
3. 对低置信度、长轨迹或高风险动作，交给更强模型或用户确认；
4. 暂不允许模型直接执行不可逆的浏览器动作。

Decider-2B 的可用性明显高于当前 NanoJev 结果，但它仍然受到长轨迹退化、校准不足和合成数据偏差的限制。NanoJev 的当前高分不能证明它理解了真实用户意图。

## 2. 两个模型分别是什么

### NanoJev

NanoJev 不是让模型逐字生成一段回答，而是在 Qwen3-0.6B 上增加一个“决策头”。输入浏览器状态后，它直接给出几个候选意图的概率，例如：

```text
research_topic       0.62
inspect_repository   0.21
unknown              0.17
```

它的优点是输出结构固定、速度方向明确，并且适合做“选择哪个候选”的任务。它的缺点是小模型容易记住页面文字、模板和关键词，而不是真正理解轨迹。

### Decider-2B

Decider-2B 是一个约 20 亿参数级别的 typed decision 模型。它同样直接返回候选选项和概率，而不是要求程序从自然语言中猜测答案。

它更适合做：

- 当前轨迹属于哪类任务；
- 哪个候选意图最可能；
- 是否应该继续、观察、升级或停止；
- 给出概率后交给程序做门控。

本次实验只做了本机推理，没有在本机重新训练 Decider-2B。

## 3. 运行条件

| 项目 | 实际条件 |
|---|---|
| 操作系统 | 原生 Windows |
| GPU | NVIDIA GeForce RTX 4070 Ti SUPER |
| PyTorch | 2.11.0+cu128 |
| Transformers | 5.16.1 |
| 数值精度 | BF16 |
| NanoJev 基座 | Qwen/Qwen3-0.6B |
| Decider 模型 | Mapika/decider-2b |
| 运行方式 | 本地 CUDA，无远程 API 调用 |
| 浏览器数据 | Edge History 只读读取，原始 URL/标题不写入结果 |

### 模型大小与显存说明

| 项目 | NanoJev | Decider-2B |
|---|---:|---:|
| 参数规模 | Qwen3-0.6B 基座，约 6 亿参数，另加决策头 | 约 20 亿参数 |
| 本地权重/检查点大小 | 本地训练检查点约 2.39 GB | 下载到本机的模型权重约 3.76 GB |
| BF16 权重理论大小 | 约 1.2 GB，实际还会有模型结构和运行开销 | 约 4 GB，实际还会有模型结构和运行开销 |
| 本机运行情况 | 已成功运行 CUDA 推理 | 已成功运行 CUDA 推理 |
| 精确推理峰值显存 | 本次没有单独测量 | 本次没有单独测量 |

这里的“约 3.76 GB”是 Decider-2B 本地权重文件大小，不等于完整推理显存。推理时还需要模型运行空间、输入上下文的 KV cache 和 CUDA 开销；上下文越长，显存通常越高。本实验确认它可以在 16 GB RTX 4070 Ti SUPER 上运行，但没有把推理峰值显存作为独立测量项记录，因此不能把训练峰值显存当成 Decider-2B 的推理显存。

### NanoJev 实际运行

已有两组本机 GPU 记录：

- 小型 smoke 训练：210 个训练问题，训练 30 步，约 136.5 秒，峰值显存约 15.76 GB；
- 较大实验：1000 条数据，训练 100 步，约 617.9 秒，峰值显存约 15.89 GB；
- 长轨迹推理测试：29 个状态、5/10/20/50/100/200 步输入，约 19 秒。

这些是实验性训练/验证条件，不代表浏览器插件每次请求都需要这么多显存。训练时显存主要消耗在 Qwen3-0.6B 基座和反向传播；实际部署只需要推理显存。

### Decider-2B 实际运行

本机使用已经下载到本地的 Decider-2B 权重进行 CUDA 推理：

- 旧版 68 条 test/OOD 数据约 10.7 秒；
- 修正数据切分后的 416 条 calibration/test/OOD 数据约 79.3 秒；
- 后一组约为每秒 5.2 条状态，约 0.19 秒/状态。

### 实际推理速度对比

| 模型 | 实测状态数 | 总耗时 | 平均单条状态 | 吞吐量 |
|---|---:|---:|---:|---:|
| NanoJev | 29 | 约 19 秒 | 约 0.66 秒 | 约 1.5 条/秒 |
| Decider-2B | 416 | 约 79.3 秒 | 约 0.19 秒 | 约 5.2 条/秒 |

按当前实验脚本的测量结果，Decider-2B 的单条状态处理速度约为 NanoJev 的 3.4 倍。但这不是严格的底层模型速度对比：两者使用了不同的推理脚本、不同的测试规模，也没有统一批大小、模型常驻方式和 CUDA 优化。因此这个结果只能说明“当前可运行路径下 Decider-2B 更快”，不能证明 Decider-2B 在所有部署方式下都必然更快。

上述速度是逐条实验脚本的结果，不是经过批处理、常驻进程、CUDA Graph 或插件网络优化后的最终响应延迟。报告中的 NanoJev 19 秒是 29 条状态的长轨迹推理总耗时，不能与 NanoJev 的训练耗时混淆；NanoJev 的 136.5 秒和 617.9 秒是训练时间，不是单次推理时间。

## 4. 数据是否有效

本地数据分成两类，必须分开理解。

### 合成 Browser Observation 数据

修正后的 v3 数据包含 871 条决策记录，切分规则如下：

- 同一个模板家族不会跨 train、calibration、test、OOD；
- train 包含 9 个意图类别；
- calibration 140 条、test 138 条、OOD 138 条；
- 重复输入为 0，冲突标签为 0，family 泄漏为 0；
- 长度档位为 5、10、20、50、100、200 events。

这说明数据切分结构是合格的，但标签仍是“完成任务后的标签”，不等于用户在真实浏览时的潜在意图。

### 本机 Edge 历史 trace

Edge 历史被转换为：

- 379 个有效会话；
- 35,641 条前缀 trace；
- 只保留粗粒度页面类别、相对顺序和浏览器 transition 类型；
- 不写入 URL、标题、域名、查询词、路径、时间戳或 URL 哈希；
- 不产生网络请求。

这类数据可以回答“用户接下来更可能访问哪类页面”，但不能直接回答“用户真正想完成什么任务”。

## 5. NanoJev 准确度与可信度

### 表面结果

在较大的合成实验中：

| 指标 | test | OOD |
|---|---:|---:|
| 样本数 | 40 | 40 |
| 意图准确率 | 100% | 100% |
| 平均置信度 | 100% | 100% |

如果只看这张表，NanoJev 看起来已经很好。但这个结论不能用于真实浏览器场景。

### 关键反事实测试

将 URL、标题、元素文字、事件目标等词汇替换成占位符，只保留轨迹结构后：

- NanoJev 准确率降为 0%；
- 模型仍然保持约 80.9% 的平均置信度。

这说明它主要依赖词汇和模板线索，而不是可靠地理解浏览行为。换句话说，NanoJev 当前更像“训练集模式识别器”，还不是可靠的浏览器意图模型。

## 6. Decider-2B 准确度与校准

### 修正切分后的结果

| 数据集 | 样本数 | Accuracy | Macro-F1 | NLL | ECE |
|---|---:|---:|---:|---:|---:|
| test | 138 | 76.81% | 49.05% | 0.967 | 29.44% |
| OOD | 138 | 99.28% | 79.71% | 0.578 | 40.99% |

这里的 OOD 结果较高，主要因为当前 OOD 家族组成相对容易，不能理解为“模型对所有新网站都能达到 99%”。Macro-F1 比普通准确率更能反映类别不均衡下的实际表现。

### 概率校准

概率校准的意思是：模型说“90% 把握”的样本，长期统计上最好真的接近 90% 正确。

本次使用独立 calibration split 拟合温度参数：

- 温度参数：1.6766；
- calibration NLL：从 1.4929 降到 1.3250；
- 但 test ECE 仍为 29.44%；
- OOD ECE 仍为 40.99%。

因此，校准有改善，但还不能直接用于“置信度超过某个阈值就自动执行”。

## 7. 长轨迹表现

Decider-2B 在 test 集上的意图准确率：

| 输入长度 | 准确率 |
|---:|---:|
| 5 events | 100.0% |
| 10 events | 75.0% |
| 20 events | 72.0% |
| 50 events | 70.0% |
| 100 events | 57.1% |
| 200 events | 28.6% |

从 5 步到 200 步下降了 71.4 个百分点。实际含义是：把整个浏览器历史或很长的事件流直接塞给模型，会让模型越来越难分辨“当前任务主线”和“无关噪声”。

更合理的工程方案是：

- 只保留最近一段事件；
- 对旧事件做摘要；
- 按会话或任务边界分段；
- 在高不确定性时重新请求更强模型，而不是继续扩大上下文。

## 8. 推荐的实际使用方式

### 可以使用

- 预测用户可能进入的页面类别；
- 对几个候选意图排序；
- 作为插件侧的预筛选器；
- 低成本判断是否值得调用更大模型；
- 给用户展示“可能是……”而不是直接替用户操作。

### 暂不建议使用

- 自动点击、发送、购买、删除等动作；
- 仅凭 0.8 或 0.9 的置信度执行高风险操作；
- 将 Edge 历史的页面类别当作用户真实意图；
- 根据当前合成数据的 100% 结果宣称模型已经理解浏览轨迹；
- 把 200 步以上原始事件直接作为输入。

## 9. 最终结论

| 模型/组件 | 当前评价 |
|---|---|
| NanoJev / 0.6B | 适合继续研究 typed decision 和本地低成本实验；尚不能证明真实语义能力 |
| Decider-2B | 比 NanoJev 更适合候选排序和升级路由；仍需校准和长轨迹处理 |
| Edge 历史先验 | 适合个性化行为预测；不是语义意图真值 |
| 当前浏览器插件 | 可以做本地预测提示和路由，不应直接自动执行高风险动作 |

最终定级：

> **当前系统适合“候选排序 + 低置信度升级”，不适合作为未经升级的常驻 Browser semantic layer。**

要进入常驻部署前，至少还需要一批人工确认的真实/半真实 Observation trace，包含跨网站、模糊意图、反事实样本和多用户测试，并在这些数据上重新训练、校准和验证长轨迹曲线。
